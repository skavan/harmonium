# Harmonium YAML v2 experiment

This directory is isolated from the live `../config/config.json`.

## Authoring model

The primary object is a **view**. Each file under `views/` describes one
user-facing destination and should be understandable on its own, even when it
grows to 200–300 lines.

View kinds are:

- `overview` — the top-level collection of rooms (less ambiguous than “home”).
- `room` — the normal landing view for a physical remote.
- `activity` — controls for an active experience such as Watch TV or Music.
- `group` — a focused collection or picker such as Comfort, Apps, or a library.
- `device` — an optional hand-authored device view; most device detail views can
  still be generated by the engine.

The room owns its activities. For example, `views/porch.yaml` contains the
Porch activity definitions, their HA scripts, contexts, state hints, physical
control targets, visible presets, device group, and page layout. Reading that
one file gives a complete picture of the Porch room.

Activity and group files likewise contain their concrete entities, controls,
buttons, and tiles. Some repetition is intentional: local comprehension is
more valuable here than maximizing reuse.

## Shared boilerplate

Only application infrastructure is shared in `system.yaml`:

- theme
- navigation entry points
- physical-button hold policy
- hardware keymaps and remote profiles
- entity-level display exceptions

A future HA GUI would generally hide or separately manage this file. It is not
page content.

`config.yaml` is consequently tiny:

```yaml
version: 2
system: !include system.yaml
views: !include_dir_named views
```

This uses Home Assistant-style include syntax. The filename becomes the view
key, and each document repeats that key as `id` so renames and copy/paste errors
can be validated.

## Build

From the repository root:

```powershell
uv run yaml/build_config.py
uv run yaml/build_config.py --check
```

The compiler resolves includes, collects activities declared by room views,
converts authoring terms (`view`, `kind`, `layout`, `header`) to the current
runtime terms (`screen`, `class`, `sections`, `banner`), expands activity tiles,
and writes `yaml/config.v2.json`.

The generated JSON retains the v2 `input`, activity `controls`/`state`, screen
`view_kind`, and `control_target` metadata. The current engine ignores fields it
does not yet understand. Input routing will eventually use these fields for the
short-press-controls-target / long-press-navigates-app model.

## Legacy file

`dashboard-harmonia.yaml` remains untouched as a migration reference. Its good
ideas are represented directly inside the relevant views. Lovelace renderer
nesting, Mushroom options, generated ids, and inline activity orchestration are
not imported; activity orchestration remains in HA scripts.
