# Icon sets — anything HA has installed

Status: **BUILT** (0.87; recut 2026-09-02). Rulings: "support anything HA has installed" (2026-08-31); "live preview in the studio and then mint into the deployed artifacts" (2026-09-01); and the HA-picker recut (2026-09-02, his tile-card screenshot): "The search starts from the first key across multiple icon sets."

## The model in one paragraph

The remote never loads a pack: every referenced `<set>:<name>` is resolved at deploy and its path data MINTED into the deployed config (`config.icon_paths`), so the panel renders inline SVG with no pack, no file, no network — the same place HA's own frontend ends up (per-icon path data), reached at deploy time instead of runtime. The Studio previews through the SAME resolver, so preview and remote can never disagree. Harmonium never redistributes a set — everything resolved comes from an artifact the user installed themselves.

## Sources (custom_components/harmonium/icons.py)

`phu:` — Custom Brand Icons, regex-extracted from the installed HACS module (no JS engine). `mdi:` — HA's own frontend ships every MDI path as JSON (`hass_frontend/static/mdi/*.json`); no network, present on every install. `material:` is the bundled font, never a set. Parsed packs cache by source mtime — a pack update invalidates, a keystroke never re-parses.

**hass-custom_icons, first-class (round 4 — his fa6-solid: mystery)**: thomasloven's `custom_icons` integration is a python icon service in the SAME process — its collections (local SVGs, Fontawesome Pro, webfonts, the whole Iconify universe) answer sets/list/icon as plain awaitables. Harmonium's API asks it directly (guarded import; not installed = not a source): every set the user ACTIVATED in its panel joins the cross-set search, the per-set autocomplete, and preview resolution — no browser, no bridge, no declaration needed. Its IconData normalizes through `ci_icon_to_path` (fapro path+path2 concatenate; an Iconify body of pure `<path>` elements extracts, box from left/top/width/height; transforms or non-path elements are an honest None), and every resolved ref is immediately BANKED as a distilled file, so the sync world — deploy minting, the engine's mask fallback — owns it from then on. Discovery's server half (`?sets=1`) lists these as "already live"; only module-only packs still go through the declared-prefix bridge below. Also round 4: `?resources=1` now includes the frontend extra-module channel (`add_extra_js_url`) — integrations inject their module THERE, which never shows in the lovelace resource list, so discovery had missed installed packs.

**The distilled-file fallback**: `www/harmonium/icons/<set>/<name>.svg` is both the hand-dropped escape hatch and where studio-resolved custom icons land. A file in the simple one-path shape parses back to (viewBox, path), so a set with no python source still resolves, previews, autocompletes, joins the search, and MINTS. Ownership stamps everywhere (the skins/logos contract): a hand-replaced SVG is never overwritten.

## Search — HA's model, not pack-shipping (the 2026-09-02 recut)

The first cut pulled a WHOLE pack per set into the Studio (`all=1`) and filtered locally. phu (~2k icons) hid the flaw; mdi (~7,400 paths, ~2MB of JSON) sat behind an empty dropdown for seconds — "slow or non-existent". HA never moves a set anywhere: it fetches one icon's chunk on demand and caches per icon. So:

- `GET /api/harmonium/icons?search=<frag>` — ONE query, every installed set: prefix matches lead inside each set, sets interleave round-robin so mdi can't drown a small pack, 60 rows max, each row carrying set + viewBox + path (the preview needs no second call). Hyphen/underscore agnostic — an mdi-habit "door-o" finds phu's `door_open`.
- `?list=<set>&q=<frag>` — one set's autocomplete, 60 rows per keystroke, per-(set, fragment) cached Studio-side. The whole-pack `all=1` path survives for tooling but nothing in the Studio uses it.
- The IconPicker searches from the FIRST key with no prefix: bundled material names (prefix-ranked — "door" surfaces `door_open` above every `*_indoor` that merely contains it, cap 12) + the cross-set rows + the custom-set bridge below, every row set-prefixed with its real glyph. Typing `set:frag` narrows to that set. An in-flight fetch shows a "searching…" row — loading must never read as an empty set.

## The custom-set bridge — packs the integration cannot parse

Every other icon pack (`fa6-*:`, `hue:`, `si:`, …) exists only as a lovelace JS module that registers itself with the HA frontend: `window.customIcons[set] = { getIcon, getIconList }` (developers.home-assistant.io 2020-05-09; older packs register `window.customIconsets`). The integration can't run JS — so the Studio does exactly what HA's frontend does: `?resources=1` lists the lovelace resource module URLs, the Studio imports them, and asks each pack's OWN resolver. Name lists come from `getIconList` where offered; sets without a listing still resolve by exact name.

**The declaration gate (round 2, ruled: "ask users to add the icon prefixes they care about")**: the bridge only runs for set prefixes listed under Theme → Icons → Icon sets (`global.icon_sets`, e.g. `fa6-solid, hue`; round 3 moved it to Theme). With nothing declared — the default — the bridge is INERT: no resource list fetched, no module imported, nothing that can hang or cost anything; the picker is material + phu + mdi + banked files. A prefix cannot name its module (packs only announce themselves by running), so a declared set's first use still loads the whole resource list — which is why declaring is the opt-in. An undeclared prefix keeps the honest warning, which points at the Theme field. **Discovery** ("Find installed packs", round 3: "read available iconsets and offer them"): one explicit click runs the bridge once — sandboxed, deadline-bounded — and offers every registered prefix as a ＋ chip; built-ins and already-declared prefixes are filtered out. That click is the only way the bridge runs without a declaration.

**The blast-radius rules (round 2 — his live report: the picker "sat there for ages with a spinning wheel and thereafter stopped doing anything")**: the imports run inside a hidden same-origin IFRAME, so a pack that throws, patches globals, or registers clashing custom elements wrecks the sandbox, never the Studio; and nothing in the bridge is awaited without a deadline (whole load 6s, each pack's listing 2.5s, each single icon 1.5s — a hung promise costs its bound and is abandoned). The picker never gates on the bridge either way: server results render as soon as they land, custom rows join late.

Every browser-side answer is handed back: `POST /api/harmonium/icons` `{ref: {viewBox, path}}` → a distilled file under the ownership stamps (path data validated — SVG path grammar only, 20KB cap; `material:` refused). From then on that set previews, searches, and mints server-side with no browser in the loop — which is what makes DEPLOY honest: minting is python and runs with no page open, so it mints what the Studio banked. An icon picked in the Studio was resolved (and therefore banked) at pick time; a ref that arrived by other means (an imported config, hand-typed while the pack was missing) banks the first time any Studio previews it, and until then falls back per the render ladder below.

## Rendering on the remote (src/ui/tiles.js — unchanged by the recut)

Minted icons render inline `<svg><path>` and are INK-FIT after mount: the pack's viewBox is re-cut to the path's own ink box padded to the material live-area ratio (~83%), wide wordmarks fit by geometric mean at true aspect with the host span widened in em. Icons paint currentColor (`--tacc` tints, `--tink` inks). A ref that never minted falls back to the mask-rendered file URL, then to the neutral glyph, with dead URLs remembered (no 404 per state diff). Chromium 61 floor holds throughout.
